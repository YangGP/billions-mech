# 开发任务与 AI 交接规格

2026-11-09 整理，沿用原 P0–P8 的20个任务包与验收要求。**下文第4–6节是原始实施规格，不是当前待办或已完成清单。** 代码已推进到0.5.89；当前完成度和下一个任务只查[开发计划](development-plan.md)，不要从旧0.5.27基线重做迁移。

**敌人要求已更新且代码已接入**：按[机械敌人设计稿](enemy-roster.md)，普通单位为建造者三形态与回收者，另有五类独立精英。长足者按最新要求可无视墙并免崎岖减速；没有部件破坏。旧原型机资源、导演校验/编成及专用表现已清理；下文历史P4b/P4c的“原型机语义不变”不再作为实施要求。接手查[接入记录](../validation/enemy-integration.md)，优先补原生机制、生命周期及波次验收，不能重复实现已有机制。

- 已有31类基础建筑/22升级形态/4单位。开局600币、80金属矿、2侦察机；主脑8/2/6容量、电10/冷4/覆盖6。当前参数以[数值表](values.md)及 Resource 为准。
- 已有整数钱包、环境电源、合金加工、科技升级、驻防/合同、区域预算，不再另建第二套相同系统。P7策略、P6b构成和完整玩法证据尚有缺口。
- 最新修复及48脚本/49项既有回归证据见[0.5.89记录](../validation/review-fixes-0.5.89.md)，不继承为原生交易或整局验收通过。
- 已完成的功能补验，未完成的功能按当前计划接续。下文历史分步中的“先不切电60”等迁移限制仅适用于当时输入，不得据此回退当前数值。
- 原生工具可用就验收；不可用则记录具体未验项，继续代码/引擎检查，不反复要求用户重启客户端。

## 2. 所有任务包共用的约束

1. 先读根目录`AGENT.md`：成熟模块→引擎内置→既有模块，记录复用结论；若按外部算法思路重写，先按仓库要求下载源码并分析。不要为经营功能更换导航、HUD或实体框架。
2. 不编写新测试脚本。用Godot导入/语法、既有`validation/vision_checks.gd`、内容一致性核对及原生玩法记录；只为配置迁移维护现有fixture，不删用例来换通过。
3. 模拟是权威。所有付款、订单、升级、驻防与自动化走`commands/sim_command.gd`、`command_queue.gd`、`SimCore.validate_command/execute_command`；HUD不直接扣资源或改实体。
4. 资源ID固定`coins/metal_ore/fuel/alloy/crystals`。材料为整数，冷却为十分之一点；保留整数余数，禁用浮点钱包。余额/实付/快照不得共享可变字典。
5. 建筑/队列下单即预留；单位出厂只转移，不重占。先全部校验，再一次扣费并登记状态；失败不能留下占位、预约或半笔扣款。同tick竞争以既有命令顺序为准。
6. 普通掉血、回血和维修不得刷新供给、环境采集区、光环或行军场。结构/运营变化才标脏；同tick合并更新。
7. 地形全局行军场保持静态，墙破口和占用只走既有局部分区。供电图需要检查远端连通性，不等于可以重建全图行军场；断开桥接中继后也不能只更新中继身边几格而漏掉整片断网区域。
8. 新建筑必须同时具备定义、生命周期、校验、快照、白模/拾取/预览、菜单状态和原生操作；不得仅把JSON的“暂未开放”改成可点。菜单ID沿用已有目录，升级形态不另塞一排重复卡片。
9. 不做本轮范围之外的六项终局工程、美术替换、正式存档、运输物流、库存上限、动态天气、昼夜发电、飞行系统和主动技能。
10. 一个任务包完成一个可运行提交。不同AI串行交接核心代码；确需同时工作时先约定文件责任，`sim_core.gd`、内容schema、全局配置和HUD只保留一个整合者，不以同时编辑同一文件来并行。

## 3. 先统一接口，再分包

以下约定是原任务的接口目标；大部分已有实现。接手先查实际类/方法及调用链，不根据本表新建同名子系统。

| 范围 | 接口/状态约定 | 落点 |
|---|---|---|
| 供电覆盖 | 返回连通供电源、发生覆盖变化的格子/区域、覆盖revision；只更新变化区域的覆盖/探索 | `grid_state.gd`及必要的独立纯数据供电模块 |
| 环境电源 | 预览返回本体、采集区、评分/预计电量、冲突格和拒绝原因；订单使用同一校验；按entity_id预约/释放 | 建造系统与环境规则适配模块 |
| 供给 | 建筑/订单需求、实际运行供给分开；未知配方或科技失败必须先于扣费；预览和结算复用同一份有效规则 | `economy_system.gd`、`sim_core.gd` |
| 科技 | `core_level/tech_level/ever_produced_alloy`与统一可用性查询；预览、直接建造、升级、生产和合同全复用 | 独立科技规则或SimCore的纯数据子模块 |
| 加工 | 每炉保存已投入配方副本、已投入资源、进度、周期产出、运行/等待原因；结束/取消/毁坏各结一次 | 加工定义Resource、建筑状态或加工系统 |
| 升级 | 每建筑保存当前定义、目标定义、差价实付和增量预留；旧级服务保持；完成时替换该实例的定义 | `building_state.gd`、升级规则模块 |
| HUD | 所有拒绝理由来自模拟；未实现/科技未满足/余额不足/位置非法分开，不能把缺料当作未开放 | `map_hud.gd`、`build_menu.gd`、`main.gd` |

现有升级通过 `MechBuildingDefinition.upgrade_to` 关联不同ID的不可变等级 Resource；注册表实体ID保持不变。实例保存当前/目标定义及实付，不得照搬旧“同building_id＋next_level”建议改坏现有内容schema。普通建筑预览、升级、生产、合同共用科技查询和真实付款入口。

命令以 `commands/sim_command.gd` 为准。普通放置使用 `building_id/origin`；升级使用 `entity_id`；驻防入口目前提交 `unit_id`、模拟选择附近可达碉堡，撤离提交 `building_id`；区域复用普通建造/生产命令，任务ID不授予绕过校验的权限。预算语义见[建造经营](building-economy.md#6-经营循环与区域预算)。

SimCore在tick内建议按“既有收益/加工结算→工程/升级完成→合并覆盖及供给变化→订单出厂→既有战斗→合并结构变化→发布状态”接入，保持命令串行与同tick可见结果一致；不要为每个新系统各发一次完整快照。明确并记录新完工/新恢复设施从哪一tick开始产出，不能依赖字典遍历顺序。

### 3.1 开发默认与正式平衡

以下是原计划采用的开发样本，其中基础经济及四单位参数已经接入；正式平衡仍需常速试玩，实际值查数值表：

- P2/P3经济联调暂关闭“8节点提前首波”，配置为固定实际首批出兵10:00、9:30预告；不能把“10:00开始预告、10:30出兵”混记为10分钟首波。保留发展度触发开关，P8单独确定正式评分/阈值，默认值不能伪装成已调平衡。
- 侦察机先做地面轻单位：建议HP60、伤害6/1秒、射程4、索敌6、移速3、视野9；卫兵战斗参数保持当前100HP、10伤害/0.8秒、射程4、移速2.5、视野7，但配方切换20币/2矿/调度2。侦察机20币/2矿/12秒/调度1。
- 常规重装、磁轨兵的完整战斗值在P4c/P6前写进同一数值稿。若无人补数值，可先用建议样本：重装HP700、伤害45/1.5秒、射程5、索敌7、移速1.8、视野7；磁轨HP600、伤害180/3秒、射程9、索敌11、移速1.8、视野9。它们只是可运行的自动攻击单位，不隐含穿透、护甲或范围伤害。
- 新资产的感染价值和发展度不要直接随退款或变动价格反复计算。先保留已明确的`infectable`，在各新定义中明确值/权重；数值校准另记。墙、门、陷阱、被动中继不因字段复用意外参与感染。

这些默认应进入Resource/配置并在交付中列出，交接人可统一调整；执行AI不应在多个系统各埋一份不同常量。

## 4. 原始任务要求：版本A——基础经济与工业升级

### P0/P1-R：接手核对与交易闭环补验

**输入：** 上述0.5.27-dev交接提交。**交付：** 可复验基线、当前代码的交易问题修复、后续接口约定；不提前换新经济数值。

实施顺序：

1. 核对菜单改动完整并记录起始提交/工作区；执行既有检查，保存同图同参数的`--perf`基线。
2. 审查暂停连续下单、墙线预算、取消重复请求、工厂队列、单位出厂、主动拆厂/被毁厂、基座重建与重开清账。发现问题先修，不新建兼容钱包。
3. 固定源于真实运营变化的供给标脏入口；检查普通伤害不触发全图/供给重建。
4. 把3.1的默认值及尚待平衡项写入数值稿；准备首波迁移开关，但先保持现行默认直到P2d配套切换。

**主要文件：** `sim/resources.gd`、`economy_system.gd`、`construction_system.gd`、`production_system.gd`、`building_state.gd`、`sim_core.gd`、`content/foundation_settings.gd`。

**验收：** 钱包差额能按逐笔实付解释；失败不扣款、重复取消不重退；出厂前后总调度不变；毁坏与拆除退款不同；重建重新申请额度且退本次实付；当前可玩开局仍可运行。原生无法操作就记录缺口，此包不能宣称经济人工验收完成。

### P2a：连通供电、中继与冷却塔

**交付建筑：** `relay_node`（B08）、`cooling_tower`（B09），为P2d切换启动参数做准备。

1. 在现有覆盖能力外接入主脑为根的中继连通图。中继完工且与根连通才可扩覆盖；断开的环不能自供电。连通算法优先评估Godot图能力/已有模块，不另写一套导航。
2. 几何沿用目前“离建筑占地最近格”的圆形半径规则，覆盖6格；中继1×1，以其格是否在连通源范围内建立关系。多路径连接可以冗余，不依赖放置先后决定最终连通。
3. 覆盖变化输出格子差集，仅重判受影响建筑的`powered`、覆盖探索和覆盖显示。可检查供电源图的整体连通，但不能重新计算地形行军场。覆盖revision与导航结构revision拆清，**仅覆盖变化不等于路径阻挡变化**。
4. 冷却塔全基地供冷12、耗电1、零调度；中继耗电1、零调度。只有完工运行才提供服务；施工按需预留，拆除停服，被毁基座保留占地但撤供给；取消拆除恢复服务。
5. HUD显示缺电、缺冷却、断覆盖各自原因；超载时恢复设施仍可按自身需求下单，不能对所有建筑一刀切拒绝。

**主要文件：** `sim/grid_state.gd`、`economy_system.gd`、`construction_system.gd`、`sim_core.gd`、`content/building_definition.gd`、新增建筑`.tres`、`coverage_view.gd`、`vision_system.gd`。

**验收：** 串联断开使远端停运、平行冗余保活、补建恢复；孤立环不供电；拆除/取消/基座不残留供给；冷却塔不要求贴节点；普通受伤不算图；覆盖变化不重建全图导航。此包不单独把主脑电60改10。

### P2b：风能与太阳能环境采集

**交付建筑：** `wind_station`（B07）、`solar_station`（B31）。依赖P2a的覆盖与运营口径。

1. 本体分别1×1、2×2；采集区向外各扩3格，分别7×7、8×8。两种矩形都按整数格范围保存，不能把太阳能区误做7×7或偏移半格。
2. 同类完整采集区不重叠，异类可重叠；按entity_id统一预约。下单即预约，基座保留、重建不重复申请，取消施工/拆完/清基座才释放。
3. 风能用二倍整数评分：风口/崎岖2、普通开阔1，`电量=min(18, score2/4向下取整)`；太阳能开阔1分，`电量=min(20, score/2向下取整)`。排除本体、障碍、水、地图外、未探索格；风口和崎岖取最高，不叠分。
4. 灰色已探索地形计分，不要求实时VISIBLE。预览只返回允许公开的信息，黑雾不贡献评分，也不能通过错误原因或冲突高亮暴露未知地形。
5. 预览、正式下单、重建复用同一规则。0产量拒绝；完工/恢复运行才加电。附近普通建筑、移动单位、受伤不改变环境评分。
6. 供电潜力与当前运行供给分开。新探索格由模拟层一次收集，按采集区反查受影响电源；不要每单位移动一次扫描全图/全部电源。简单区块索引足够，不做额外行军场。
   将实际电量放入实例运行状态/有效规则，改造`economy_system.gd.recompute`目前直接累加`definition.power_provided`的路径；不得给每个选址修改共享电源Resource，也不能只在HUD显示动态值而账本仍加固定电量。
7. 原生预览绘制本体与采集区两个轮廓、预计电量及冲突格，鼠标移开HUD不误放置。

**主要文件：** `building_definition.gd`、`building_state.gd`、`construction_system.gd`、`vision_system.gd`、`sim_core.gd`、`map_definition.gd`、`coverage_view.gd`和放置预览路径。

**验收：** 满分/边缘/黑雾/灰区、同类冲突、异类重叠、连续订单竞争、暂停、取消、摧毁基座/重建/清除均一致；同址强化未来乘2不改区。基础零燃料电源在电力/调度赤字时仍有恢复路径。

### P2c：地图环境与开局选址复核

1. 以`development_basin_128.source.json`为布局源，补齐风口与水域的明确环境层；水域先只作环境标记和不可建/通行语义，不新增水库存。保持128×128，不重随机地图。
2. 维护`tools/compile_development_map.py`同源输出原生`.tres`、bundle、布局报告，不能只改编译结果；燃料源预留到P3a才映射为可采原生矿点。
3. 在真实启动覆盖/探索下核对参考风能位(57,60)、太阳能位(68,59)、西侧金属站/中继位。已有布局总分不等于开局已探索后的实际分，发现差异应微调布局或启动探索，不能让评分偷偷读取黑雾。
4. 在同一正常游戏配置中找到合法的风能≥12电和太阳能≥14电位置；留足5×5主脑、节点/冷却/矿站和防线通路。可以跨类型重叠采集区；不强迫每局必须两种都造。

**主要文件：** 地图源/编译器、`content/map_definition.gd`、`grid_state.gd`、`content/development_128.tres`；修改地图时按generate2dmap技能复用既有数据/连通工具，不新增美术生成流程。

**验收：** 编译一致、矿点/出生/四隘与原34目标连通不退化；启动有效评分满足预算；水域不被当普通开阔地；无水区域仍可发展。原生迷雾保持开启。

### P2d：一次切换无燃料开局与基础军工

依赖P2a–c可运行后再合入这一包，不能先单独降低主脑供给。

1. 按V1/V2同步切换：开局600币/80金属矿/其余0；主脑总8/系统2/净6、电10/冷却4/覆盖6、币4/min；节点总4/系统1/净3、电2/冷却2、币6/min。建筑价格/产率从V2取值，不能只改HUD。
   主脑/节点系统自用只计入`capacity_system_reserved`，不再同时计`capacity_cost`向外部调度池扣一次；容量供给只在完成运行时增加，施工仍预留其真实电力/冷却。
2. 初始2名侦察机；`starting_unit_id=scout`，合法出生点与5×5主脑不重叠。明确移除/关闭额外免费验证实体，避免它成为第三个不占容的侦察单位；诊断实体只在显式诊断配置启用，保留既有视野fixture的对应设置。
3. 组装厂产品`[scout,sentinel]`，100币/10矿；卫兵20币/2矿/调度2，侦察机20币/2矿/调度1。队列同时支持两种工期，出厂/取消按订单自身规则。
4. 切换金属站、墙、炮塔、冷却/中继/电源的完整新配方，不新增燃料/合金门槛。展示建筑调度、单位、队列、系统预留分项。
5. 首波迁移采用3.1的固定时间默认；从模拟快照发布预告/出兵时间和粗方向，暂停冻结倒计时，不用UI自己估算。保持四波胜负作为版本A范围。
6. 复核新冷却与调度下的施工次序：满容/超载可补零调度恢复设施；缺电先建零耗电电源，缺冷却可建冷却塔；超载中继仍需要1电，不能豁免真实需求。

**主要文件：** 开局及全部基础`.tres`、`foundation_settings.gd`、`unit_definition.gd`、`unit_system.gd`、`production_system.gd`、`wave_director.gd`、`sim_core.gd`、HUD与菜单。

### P8：最终对账、正式节奏与性能验收

1. 清点31类及全部升级的定义/前置/菜单/状态/损失/恢复路径；六项终局工程仍排除，不以空按钮凑数。

## 7. 验证与交付格式

在仓库根目录、Godot可用时使用现有入口（`godot`在Windows可用本机`D:/Tools/Godot/godot.cmd`等价调用）：

```powershell
godot --headless --path . --import
godot --headless --path . --check-only --script res://presentation/main.gd
godot --headless --path . --script res://validation/vision_checks.gd
godot --headless --path . --quit-after 600
git diff --check
```

再对本包所有变更`.gd`执行`--check-only --script`，发布节点检查全部活动脚本；脚本数量随新增变化，不硬编码44永远正确。检查日志中的SCRIPT/Parse/Compile错误，不只看退出码。证书读取/Steam全局设置保存的环境报错与项目脚本错误分开记录。性能使用`run.bat -- --perf`，玩法按正常时速验收；必要诊断加速与无限资源不得冒充正式开局证据。

每包交付说明固定包含：

1. 本包编号、输入基线、完成内容及未实施项。
2. 修改文件/新增内容ID/命令与快照字段；对前后包的接口影响。
3. 复用实现与源码来源/许可证，项目自写业务适配范围。

5. 导入/语法/既有回归/启动/原生交易/实战/性能分别的结果与证据；未执行明确标记。
